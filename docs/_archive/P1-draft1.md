# Phase P1 — Data + real PayPal invoices + "Start the demo" (spec)

**Goal:** the money foundation exists and is real. All tables live; an ERP export (CSV) is imported through one importer; every invoice is mirrored to a **real PayPal sandbox invoice** whose dates, amounts and lines equal ours; `POST /api/demo/start` gives each visitor their **own** Northside Jewelers copy in a few seconds. No buyer/supplier screens yet (P2/P3).
**Time box:** ~7 h (Mon night → Tue ~11:00 ET). **Branch:** `p1-data-mirror` → merge to `main` when §6 passes.
**FRs:** FR-1 (import), FR-2 (mirror), FR-12 (demo copy, backend part), FR-15 (link in invoice note). **Open checks resolved here:** 1, 6, 8, 9 (PayPal behaviours, one script).

## 0. Why P1 matters for winning (read before building)
Judges score Technological Implementation first (also the tiebreaker) and may only watch the video and click the link. P1 decides three things they will see:
1. **The PayPal invoice page looks like a real business invoice** — supplier name, item names with SKU + memo, a clear due date (past due for INV-1038), a note with the statement link. In the video we open PayPal's own page; it has to look right on its own.
2. **"Start the demo" is fast and never shared** — target **≤ 6 s** from click to a ready statement (3 invoices created in parallel), each judge gets their own copy, nothing breaks when two judges click at once.
3. **Our numbers and PayPal's numbers are identical** — totals, due dates, statuses. Any mismatch is visible, never silent. This is the base for the P2 "one payment, many invoices" moment.

## 1. In scope / out of scope
**In:** all tables + migration · money/date helpers · CSV importer · PayPal client + invoice functions · mirror service · demo seed (via importer) + seeded message/proposal · `POST /api/demo/start` (cookie, rate limit) · admin `POST /api/supplier/import` (JSON result only, no UI) · integration-test database · open-checks script · APIMatic proof.
**Out:** any page except the landing (P2/P3), statement API (P2), orders/payments (P2), webhooks/worker (P3), agent (P4). `put_adjustment` and `remind` functions are written and unit-tested now (they're invoice calls) but not wired to routes until P3.

## 2. Decisions this spec adds (also written into the other docs)
| # | Gap found while writing P1 | Decision |
|---|---|---|
| D1 | No supplier record anywhere | Single supplier per deployment: settings `SUPPLIER_NAME` (default "Demo Diamond Co."). Used in the invoice `invoicer.name.business_name`, statement header, UI. |
| D2 | Demo buyers all share `SANDBOX_BUYER_EMAIL`, so "re-import for the same buyer" can't key on email | Importer's buyer key = `(email, demo_session)`; real imports have `demo_session = NULL`. A real import matching an existing buyer updates it; a demo copy always creates a new buyer. |
| D3 | CSV has no message/proposal records but the seed needs the S-120 complaint | `demo_seed` inserts the message + pending ADJUSTMENT proposal **after** the importer, directly (with evidence computed from the imported rows). |
| D4 | A crash between PayPal "create" and our DB save would leave an orphan PayPal invoice and a retry would duplicate it | Mirror is resumable: if `paypal_invoice_id` is NULL, first `search-invoices` by `paypal_invoice_number`; adopt it if found, else create. Plus `PayPal-Request-Id = <env>-inv-<uid>`. |
| D5 | Mirror failures had nowhere to live | New columns `invoices.mirror_error TEXT`, `invoices.mirror_attempts INT DEFAULT 0`. `ledger_status` stays `DRAFT` until create+send succeed, then `OPEN`. |
| D6 | `/demo/start` time: 3 invoices × (create + send + get) + token ≈ 10 sequential calls | Mirror the 3 invoices **concurrently** (`asyncio.gather`, shared token, httpx async). Target ≤ 6 s total; measured and logged. If it's slower on Render, P3 adds a small pre-built pool in the worker (noted, not built now). |
| D7 | `detail.memo` vs `detail.note` | `note` (visible to the buyer on PayPal) = statement link sentence; `memo` (private to the merchant) = "Kept from memo M-201 · ERP INV-1038". Each item gets `description` = "SKU S-104 · memo M-201". |
| D8 | Demo cookie details unspecified | Cookie `mtc_demo` = signed (`itsdangerous` — add to `requirements.txt` — with `DEMO_COOKIE_SECRET`) demo-session id; `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=7 days`. Starting again creates another buyer in the **same** session. Passed through the web proxy unchanged. |
| D9 | Open check 6 (transaction id in record-payment response) is cheap to test now | Folded into the P1 open-checks script. |
| D10 | **Code gap:** `tests/conftest.py` sets `APP_ENV=test`, which makes settings skip `.env` — so `TEST_DATABASE_URL` in `.env` would never be seen, and `backend/db/session.py` builds its engine from `DATABASE_URL` at import | `conftest.py` reads **only** `TEST_DATABASE_URL` from the shell env or, if absent, from `.env` (single key, via `dotenv_values`, nothing else loaded), and — **before any app import** — sets `DATABASE_URL` and `DATABASE_URL_UNPOOLED` to it, so the app engine, the session and Alembic all point at the test database. |
| D11 | **Code gap:** CI already uses `DATABASE_URL=postgresql://ci:ci@localhost:5432/ci`; the earlier draft said a `test/test/test` service | CI Postgres service uses user/password/db **`ci`** on 5432, and `TEST_DATABASE_URL` = that same URL. |
| D12 | **Code gap:** the DB layer is **sync** SQLAlchemy, but the PayPal client is async | PayPal I/O is async (httpx); DB stays sync. Mirror runs the PayPal calls for all invoices concurrently with `asyncio.gather`, **then** writes results to the DB in one sync transaction — no DB access inside the concurrent tasks. Routes that call PayPal are `async def`; their DB work is short. |
| D13 | **Code gap:** missing packages | Add `itsdangerous` (signed cookie) and `python-multipart` (FastAPI file upload) to `requirements.txt`. Async tests use `@pytest.mark.anyio` (anyio ships with httpx/starlette; no new dev dependency). |
| D14 | `SUPPLIER_NAME` and settings checks | Add `supplier_name: str = "Demo Diamond Co."` to `Settings` and `SUPPLIER_NAME` to the `mtc-shared` group **in `render.yaml`** (Blueprint-managed — not typed by hand). `/demo/start` and mirroring check what they need at use and return 503 `NOT_CONFIGURED` with the missing **names** (never values): PayPal client id/secret/business email, `APP_BASE_URL`, `DEMO_COOKIE_SECRET`, `IP_HASH_SECRET`, `SANDBOX_BUYER_EMAIL`. |
| D15 | What happens to a demo copy whose PayPal mirror fails | Import + seed commit first; mirror after. If any invoice still fails after retries → 503 `PAYPAL_UNAVAILABLE`, **no token returned**; the half-built buyer stays in the DB unreachable (its token was never shown). No deletes needed. |
| D16 | Abuse cap beyond 5/hour per IP | Global cap **200 demo copies per day** (counted in `demo_rate` with `ip_hash='global'`) → 429 `DEMO_DAILY_LIMIT`. Protects the sandbox account and DB during judging. |
| D17 | Seeded proposal looks AI-made but isn't | The seeded message gets `ai_result = {"seeded": true}` and the proposal `evidence.source = "seed"`. **P4 replaces this:** at demo start the real agent triages the seeded message and creates the proposal live (so the AI shown to judges is real). Written into the P4 plan. |
| D18 | Import strictness differed between docs (APP_FLOW J5 said "nothing half-written per invoice") | One rule everywhere: **a file with any invalid row writes nothing** (all errors returned). APP_FLOW J5 updated. |
| D19 | API responses in BACKEND_SCHEMA didn't match this spec | `/demo/start` → `{statement_token, buyer_id, ms}`; `/supplier/import` → `{created, updated, errors, mirrored, mirror_errors}`; new error codes `NOT_CONFIGURED` (503), `PAYPAL_UNAVAILABLE` (503), `RATE_LIMITED` (429), `DEMO_DAILY_LIMIT` (429). BACKEND_SCHEMA §2 updated. |

## 7. Risks and fallbacks
| Risk | Sign | Fallback |
|---|---|---|
| PayPal rejects past `invoice_date` / due date (check #8) | 400 on create | Create with today's date + due = max(today, our due); our dates stay the truth on our screens; supplier screen notes "PayPal dates differ"; video avoids PayPal's due date |
| `/demo/start` > 6 s on Render | logged `ms` | Keep concurrency; P3 worker keeps 2 pre-built copies ready (pool) |
| PayPal sandbox flaky | 5xx / timeouts | Retries (3×), then 503 with a friendly message; never show a half-mirrored copy |
| Invoice business name shows the sandbox default | PayPal UI | Set business name in sandbox account (§3 step 3) and/or `invoicer.name.business_name` |
| Neon `test` branch slow from CI | n/a (CI uses its own Postgres) | — |
| Importer edge cases eat time | > 2 h on step 4 | Keep validation strict and simple; real ERP formats come after the hackathon |
