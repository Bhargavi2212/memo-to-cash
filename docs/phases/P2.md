# Phase P2 — Statement + one payment for many invoices (spec v2 after independent review)

**Goal:** the feature PayPal doesn't have, working end to end on the live site. A buyer opens their statement link, sees kept / returned / still-out lines and what's owed, pays **one** PayPal checkout for several invoices, and every PayPal invoice shows the new balance. Our ledger and PayPal agree to the cent.
**Time box:** ~10 h realistic (Tue 06:00 → ~17:00 ET). **Nothing is cut (Bhargavi, Nov 10)**: every item ships; an overrun moves P3's start, never P2's scope. **Branch:** `p2-statement`. **FRs:** FR-3, FR-4, FR-5, FR-6, FR-12 (landing start). **Open checks:** 2 (Venmo) + new 12, 13 (§5).
Review changes R1–R16 are folded into the decisions below (marked R#): R1 never VOID money PayPal holds · R2 capture Request-Id per attempt after a decline · R3 payment_source mapping · R4 P2 retry path (`/refresh`, re-POST `/capture`) · R5 `payments` timestamps (migration 0003) · R6 `next build` in CI + Suspense · R7 real lock bound · R8 missing capture states · R9 spare sandbox buyer + card fallback · R10 demo prefills $5,000 · R11 Pay Monthly wording · R12 default referrer policy · R13 one-txn/gather/one-txn recording · R14 receipt returns before recording · R15 resplit vs planned_split · R16 extra Orders errors.
**Process:** `/phase 2` Stage 1 writes `docs/phases/P2-plan.md` and stops → independent review → Bhargavi's "approved" → build.

## 0. Why P2 decides the result
The judged moments (UI_UX §7) 1, 3 and 4 all live here:
1. **Returned vs kept vs still-with-you on one screen**: the statement explains the bill without a call.
2. **One payment, split shown before paying**: our statement shows `INV-1038 $3,500 · INV-1042 $1,500` before the PayPal popup and on the receipt after. (The items are on the PayPal order, but PayPal's new checkout page doesn't display them — smoke, Nov 10.) Nothing else in the field shows this.
3. **PayPal's own invoice pages show the new balances**: INV-1038 `MARKED_AS_PAID`, INV-1042 `PARTIALLY_PAID` with $2,000 due. That is the proof that the ledger is real, not a mock.
If P3/P4 slip, a P2 that works live still makes a credible submission. If P2 is shaky, nothing after it matters.

## 2. Decisions
| # | Decision |
|---|---|
| D1 | **Split** (invariant 2). `split_payment(amount_cents, invoices, selected_ids) -> list[(invoice_id, cents)]`. Pure. `invoices` = `(id, due_on, issued_on, balance_cents)`. Order is oldest `due_on` first; ties go to `issued_on`, then `id`. Rules: only selected ids; never above a balance; sum == amount. `amount <= 0`, `amount > selected balance`, or an empty selection → `ValueError` with a code (`AMOUNT_NOT_POSITIVE`, `AMOUNT_EXCEEDS_SELECTED`, `NOTHING_SELECTED`). Defaults per BACKEND_SCHEMA §8 live in a thin `resolve_request()` wrapper, not in the pure function. Hypothesis properties: sum, cap, only-selected, order (no later invoice gets money while an earlier one has balance left), deterministic. |
| D2 | **Statement read model** (`services/statement.py::get_statement(session, token, today)`). Lookup by `statement_token`. Demo buyers require `demo_ready=true` (P1 D9). Unknown → 404 `NOT_FOUND`. **No PayPal calls on page load**: our ledger is the source (ledger rule). Computed by code, never stored:<br>- `due_cents = total - paid`;<br>- `owed_cents` = Σ due of open invoices;<br>- `past_due_cents`;<br>- `days_overdue`;<br>- `oldest_age_days` = today − `issued_on` of the oldest invoice with due > 0;<br>- line `status`, `invoice_no` for KEPT lines, `due_back_on` (memo's) for OUT;<br>- `credit_cents` = Σ `unapplied_cents`.<br>Payments listed: STATEMENT `CAPTURED` and `CAPTURE_PENDING` (R8) + OFF_PAYPAL `RECORDED` (with `applied`). `CREATED`/`VOIDED` are never listed. `notices` (last 7 days by `payments.updated_at`, R5): `PAYMENT_VOIDED`, `RECORDING_PENDING` (captured payment with any allocation not `RECORDED`), `PAYMENT_CREDITED`. Shape = BACKEND_SCHEMA §3 plus `supplier.name`, `invoices[].paypal_url` (= `payer_view_url`), and `demo_login: {email, password}` only when `DEMO_MODE` and `buyer.is_demo` (sandbox values, shown so a judge can pay). `today` = `today_ny()`. One query per table, no N+1 (statement API < 300 ms on Neon). |
| D3 | **Preview** `POST /statement/{token}/preview` = `resolve_request` + `split_payment` on current balances. No writes. 422 codes from D1, plus `INVOICE_NOT_OPEN` when a selected id isn't this buyer's or has due 0. Response adds `remaining_after: [{invoice_no, due_cents}]` so the UI can show "→ $2,000 left". |
| D4 | **Order** `POST /statement/{token}/order` `{invoice_ids?, amount_cents?, funding_source?}`:<br>1. **Txn 1** (advisory lock on buyer): split on current balances → insert payment `source=STATEMENT, status=CREATED, amount, planned_split=[{invoice_id, amount_cents}], received_at=null` → commit. **R5:** migration `0003` adds `payments.created_at` and `payments.updated_at` (default `now()`, updated on every status change) — needed for notices and the P3 sweep's "CREATED > 2 min"; Bhargavi runs it on prod before merge.<br>2. **After commit:** PayPal create order (D9) with Request-Id `<env>-ord-<payment uid>` → store `paypal_order_id` (txn 2).<br>3. PayPal failure → payment `FAILED`, 503/502 per D13.<br>Returns `{paypal_order_id}`. Each click is a new payment. Abandoned `CREATED` payments are expired by the P3 sweep and are invisible to the statement. |
| D5 | **Capture** `POST /statement/{token}/capture` `{paypal_order_id}`. The payment is looked up by `paypal_order_id` **and** the token's buyer, else 404 `NOT_FOUND`. A token can never capture another buyer's order. Then:<br>- `CAPTURED` → return the existing receipt, 200.<br>- `CAPTURE_PENDING` → 200 with the pending receipt (R8).<br>- `VOIDED` → 409 `STATEMENT_CHANGED`.<br>- `FAILED` → 409 `PAYMENT_FAILED`.<br>- `CREATED` → one DB session held across the PayPal call, the one exception in invariant 9:<br>&nbsp;&nbsp;(a) threadpool: begin, `pg_advisory_xact_lock(buyer_id)`, re-split `planned_split`'s invoices + amount on current balances;<br>&nbsp;&nbsp;(b) doesn't fit → **first GET the order (R1)**: `COMPLETED` (we captured earlier but never saw the answer) → `finish_capture`; whatever no longer fits becomes `unapplied_cents` credit (invariant 9), never VOIDED. Otherwise → `VOIDED`, commit, 409 `STATEMENT_CHANGED`, no capture call. A payment with money at PayPal is never marked VOIDED;<br>&nbsp;&nbsp;(c) await PayPal capture (D10);<br>&nbsp;&nbsp;(d) threadpool: `finish_capture` (D6) in the same transaction, commit;<br>&nbsp;&nbsp;(e) after commit, return the receipt at once; recording runs as a FastAPI BackgroundTask (D7, R14).<br>The session is used from one coroutine at a time, so no concurrent use. **R7 lock bound:** the OAuth token is fetched **before** the lock (`pp.ensure_token()`); the capture is wrapped in `asyncio.wait_for(…, 10)` (httpx timeouts are per phase, not total); any confirming GET happens **after** the lock is released (rollback) with a hard 5 s cap; the hand-carried session is closed in `try/finally` with rollback, so a cancelled request can't leak the lock. Lock held ≤ ~11 s. |
| D6 | **`finish_capture(session, payment, capture)`**: idempotent, shared with the P3 webhook and sweep.<br>- Stores `paypal_capture_id` (unique), `received_at`, `status=CAPTURED`.<br>- Allocates by re-split. If the captured amount no longer fully fits, it allocates what fits oldest-first and puts the rest in `unapplied_cents` + a `PAYMENT_CREDITED` notice (invariant 9).<br>- Inserts allocations (`PENDING`), updates `invoices.paid_cents` and `ledger_status` (OPEN / PARTIALLY_PAID / PAID).<br>- Audit `payment.captured`.<br>- Captured amount or currency ≠ ours → still store the capture, put any difference in `unapplied_cents`, log ERROR. Never lose money.<br>- Capture `status` `DECLINED` or `FAILED` in a 201 answer (R8) → no allocations, payment stays `CREATED`, handled like `INSTRUMENT_DECLINED` (402).
- If capture `status` is `PENDING` (not `COMPLETED`): payment `status=CAPTURE_PENDING`, no allocations. Receipt and statement say "PayPal is still processing your payment". P3's `PAYMENT.CAPTURE.COMPLETED` webhook finishes it. (New status → BACKEND_SCHEMA §8 state machine.) |
| D7 | **Record allocations** (`record_allocations(payment_id)`), after the capture commit. **R13 shape:** one transaction sets **every** allocation to `RECORDING` (+ `record_started_at`, `attempts+1`) and commits → `gather` **only the PayPal calls** (8 s per call, 12 s overall) → one transaction writes all results. **R14 latency:** `/capture` returns the receipt right after the capture commit (allocations shown as "updating on PayPal…") and recording runs in a FastAPI `BackgroundTask`; the receipt page polls `GET /payments/{id}` every 2 s for up to 20 s.<br>1. (in the first transaction) all allocations → `RECORDING`.<br>2. Call `invoices.record_payment(method=PAYPAL, payment_date=today_ny, amount, note="[MTC:<allocation uid>] Statement payment · PayPal capture <capture id>")`, Request-Id `<env>-alloc-<allocation uid>`.<br>3. Success → `RECORDED`, `paypal_transaction_id` = response `payment_id` (open check 6), `paypal_recorded_at`. Then `GET` the invoice → `paypal_status`, `paypal_due_cents`, `paypal_synced_at`, and `mismatch` if PayPal due ≠ our due.<br>4. Deterministic failure → `FAILED` + `paypal_record_error`.<br>5. Transient failure or timeout → stays `RECORDING`. The P3 sweep resolves it via the `[MTC:<uid>]` search (TRD §6b-3).<br>`resolve_recording(allocation)` (GET invoice → find token → mark RECORDED, else retry with the same Request-Id) is built **in P2** and used before any retry. **R4: P2 has its own retry path** (no sweep until P3): `POST /statement/{token}/payments/{id}/refresh` runs `resolve_recording` for that payment's `RECORDING`/`FAILED` allocations (max one call per allocation, 12 s cap) — FR-6 "failures stored + retried" holds in P2. P3's sweep calls the same function. The receipt reports `recorded` per allocation; it never blocks on PayPal beyond 12 s. |
| D8 | **Lock + transactions recap.** Money writes (order split + insert, finish_capture, record-state changes) each take `pg_advisory_xact_lock(buyer_id)`. Recording does **not** change `paid_cents`: an allocation counts the moment it's inserted at capture, and PayPal recording only mirrors it (ledger rule). |
| D9 | **PayPal order body**, every field confirmed via APIMatic before coding (`[apimatic]`).<br>- `intent=CAPTURE`; one purchase unit.<br>- `custom_id` = payment uid; `invoice_id` = `<env>-stmt-<payment uid>`, so PayPal itself refuses a duplicate charge for the same payment.<br>- `description` "Statement payment · Demo Diamond Co." (≤ 127).<br>- **`items`** = one per allocation, `{name: "INV-1042 (memo M-207)", quantity "1", unit_amount}`, with `amount.breakdown.item_total` = amount. The split is visible inside PayPal's window (open check 13).<br>- Experience: `shipping_preference=NO_SHIPPING`, so judges are never asked for an address; `user_action=PAY_NOW`; `brand_name` = `SUPPLIER_NAME`. **R3 mapping** from the SDK's `createOrder` `data.paymentSource`: `paypal`, `paylater`, `credit` → `payment_source.paypal.experience_context`; `venmo` → `payment_source.venmo.experience_context`; `card` or anything unknown → **no** `payment_source`, use `application_context` (shipping_preference, user_action, brand_name). The card button stays on as the judges' fallback (R9). Confirm via APIMatic + the smoke run. |
| D10 | **PayPal Orders client calls** (`backend/paypal/orders.py`):<br>- `create(pp, payment, splits, funding)`.<br>- `capture(pp, order_id, payment_uid, attempt)`: Request-Id `<env>-cap-<payment uid>` and, **after a decline, `<env>-cap-<payment uid>-<n>`** (R2: PayPal may replay a stored decline for a reused id; `n` = `payments.capture_attempts`, bumped only on a decline — needs that column in `0003`). ORDER_ALREADY_CAPTURED still prevents a double capture. `Prefer: return=representation`, **10 s timeout, no client retries** (it runs under the lock). Add `timeout`/`retries` overrides to `PayPal.request`.<br>- `get(pp, order_id)`.<br>Capture outcomes:<br>- `COMPLETED` → D6.<br>- 422 with `details[].issue`:<br>&nbsp;&nbsp;`ORDER_ALREADY_CAPTURED` → GET order → D6 → receipt 200;<br>&nbsp;&nbsp;`INSTRUMENT_DECLINED` or `PAYER_ACTION_REQUIRED` → 402 `PAYMENT_DECLINED`, payment stays `CREATED` (the SDK restarts, D15);<br>&nbsp;&nbsp;`ORDER_NOT_APPROVED` → 409 `ORDER_NOT_APPROVED`;<br>&nbsp;&nbsp;`TRANSACTION_REFUSED`, `MAX_NUMBER_OF_PAYMENT_ATTEMPTS_EXCEEDED` → 402 `PAYMENT_DECLINED`; `DUPLICATE_INVOICE_ID` → GET order → finish if COMPLETED, else 502 `PAYPAL_REJECTED` (R16).<br>- Transient / timeout → GET order once: `COMPLETED` → D6; otherwise payment stays `CREATED`, 503 `CAPTURE_UNCONFIRMED` "We couldn't confirm your payment yet — don't pay again." with a **"Check again" button that re-POSTs `/capture`** (R4: safe — same Request-Id, or ORDER_ALREADY_CAPTURED → finish).
