## 0. What judges must see (P3a)
1. From the buyer's receipt or statement: **"See it as Demo Diamond Co."** → `/supplier` shows their own Northside copy: owed, past due, the $5,000 payment already split across INV-1038/INV-1042, and **"Needs your decision (1)"** — the agent's −$20.00 proposal with ✓ checks and an "agent" badge.
2. **Approve** → "PayPal invoice INV-1051 updated: due $1,400.00" with a link to PayPal's page. If the judge had paid everything: **"INV-1051 is already paid — approve as a $20.00 credit"**, never an error.
3. The buyer's statement now shows the request as **Approved** (or the supplier's reply).

## 1. Scope
**P3a:** supplier auth (admin token or demo cookie, scoped) · `/supplier` overview · `/supplier/buyers/[id]` · `/supplier/payments/[id]` · proposals list + approve / edit / reject for every kind incl. the credit path · record an off-PayPal payment (cheque/wire/Zelle → FR-14) · copy statement link (FR-15) · "See it as Demo Diamond Co." entry points (J1 step 6) · buyer-side status/replies.
**P3b:** PayPal webhooks (FR-7) · `services/sync.py::sweep` + `backend/worker.py` (Render worker, adaptive polling) · reminders (Job C drafts + PayPal remind, 2/day) · `POST /supplier/import` + upload page + `seed/sample_export.csv` (FR-1 endpoint) · open check 3.
**Not in P3:** multi-supplier, supplier login/accounts (v1: admin token + demo cookie), refunds automation.

## 3. Decisions — P3b
| # | Decision |
|---|---|
| B1 | **Webhook route** `POST /api/paypal/webhook` on the **api's public URL** (TRD §7, not via the web proxy): verify with `POST /v1/notifications/verify-webhook-signature` (`PAYPAL_WEBHOOK_ID`) → store `webhook_events` (unique `paypal_event_id`, raw payload) → 200 always after storing; unverified → 400, not stored. Verification sends the **raw request body bytes** as `webhook_event` (spliced, not a re-serialised dict, R9). Respond 200 first; process in a BackgroundTask, then run `sweep(scope=that invoice/order)` (TRD §6b-4(a), R9) so a sleeping worker never delays it. Events: `INVOICING.INVOICE.PAID/CANCELLED/REFUNDED`, `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.COMPLETED/REFUNDED`. Bhargavi registers the URL in the sandbox app's dashboard and sets `PAYPAL_WEBHOOK_ID` on Render (dashboard — Blueprint doesn't sync). Open check 3 = a real delivery arrives and verifies. |
| B2 | **J6 backfill** (TRD §6b): invoice webhook → skip if any allocation on it is RECORDING (sweep retries) → GET invoice → `payments.transactions` not matching our transaction ids or `[MTC:<uid>]` tokens = new money → payment `source=PAYPAL_INVOICE_PAGE, status=CAPTURED` + allocation (under the buyer lock), unique on transaction id. **P2 D23 reconcile (R4)** — in **one** buyer-locked transaction: for our allocation on that invoice that is FAILED with `PAYMENT_AMOUNT_GREATER_THAN_AMOUNT_DUE`, compute the overlap with the direct PayPal-page payment; **shrink** the allocation by the overlap (or **delete** it if fully overlapped — `amount_cents > 0` forbids 0), lower `invoices.paid_cents` by the same amount, add the overlap to the payment's `unapplied_cents` (credit), **then** insert the backfill allocation; clear `mismatch` when PayPal's due equals ours. Runs from the webhook **and** the sweep (the overpay only surfaces later via `resolve_recording`, which skips `OVERPAY_ISSUE` today). Ledger rule holds: `paid_cents` = Σ allocations throughout. |
| B3 | **Lost capture / approved-but-closed** (TRD §6b-2): `PAYMENT.CAPTURE.COMPLETED` → payment by `custom_id` → `finish_capture` (P2) if still CREATED. `CHECKOUT.ORDER.APPROVED` and the sweep capture **only CREATED** payments (never VOIDED/FAILED, P2 §8) after the same split check; doesn't fit → VOIDED + notice. |
| B4 | **Sweep** `services/sync.py::sweep(scope)`: unprocessed webhook events · CREATED payments > 2 min (GET order) · CREATED/APPROVED > 3 h → VOIDED · RECORDING allocations > 5 min and FAILED transient ones → `resolve_recording` (P2) · nothing else. Idempotent; each item in its own transaction; errors logged and left for the next run. |
| B5 | **Worker** `backend/worker.py` (Render background worker, added to `render.yaml`; Bhargavi does the Blueprint manual sync): loop — run `sweep()`; **adaptive interval**: 30 s while the last sweep found work or any payment/webhook/message happened in the last 15 min, otherwise **60 min** (P2 D24: Neon must be able to sleep); Job C runs **once per NY date, on the first wake at or after 09:00**, recorded in `audit_log` (`reminders.daily_run`, date) so restarts never repeat it (R9). One query decides "activity in 15 min": greatest of `payments.updated_at`, `webhook_events.received_at`, `messages.created_at`, `proposals.decided_at` (R8 — real column names). Idle cost ≈ 24 wakes × ~5 min × 0.25 CU ≈ 0.5 CU-h/day (fine under 100 CU-h/month; recorded in P2 D24). |
| B6 | **Job C reminders** (moved from P4): daily, for invoices past due with no active PROMISE_NOTE → agent drafts `ReminderDraft` (schema §5, validator: money/day counts from facts like D4) → REMINDER proposal (PENDING). Demo copies: no daily job (only the manual "Draft a reminder" button on the buyer page, same code). B6 is the **last** P3b build step (b4, after webhooks b1, sweep/worker b2 and import b3), because open check 3 and the D23 reconcile matter more (R12). |

## 8. Carried forward
- **Overpayment as credit (cheque / wire for more than is owed).** v1 refuses it: `POST /supplier/payments/record` answers 422 `AMOUNT_EXCEEDS_SELECTED` and records nothing; the dialog disables Confirm and says "That's $X more than <buyer> owes ($Y).
